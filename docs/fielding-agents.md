# 수비·주루 Agent와 플레이 판정 (3단계)

2026-09-26 요청으로 3단계(타자·주자 + 투수 + 수비 5명) 학습을 위해 수비 이동·포구·송구·아웃 판정과 두 Agent를 추가했다. 같은 날 후속 요청으로 **주자 여러 명**(타자주자 + 1·2·3루 누상 주자)과 볼카운트·이닝 상황을 더했다([상황 규칙](game-situation.md)).

- 수비는 **1루수·유격수·3루수·좌중간·우중간 외야수 5명**이다. 포수·2루수는 없다.
- 달리기는 환경이 제공하고, 주자 Agent는 진루/귀루 판단만 한다.
- 규칙은 `PlayDirector`가 판정하며 결과의 단일 소유자다.
- 수비수·누상 주자가 없는 씬(`BaseballPlayground`, 1·2단계)에서는 새 규칙이 동작하지 않아 기존 동작과 같다. 기존 검증 5종으로 확인했다.

## 수비·주루 규칙 (환경)

| 항목 | 규칙 | 설정(`BaseballEnvironmentConfig` › 수비) |
| --- | --- | --- |
| 이동 | 명령(필드 XZ 방향, 크기 1 = 최고 속력)을 가속도 한도 안에서 따른다. 경기 경계 1 m 안쪽에 머문다 | `Fielder Speed` 7.5 m/s, `Fielder Acceleration` 15 m/s² |
| 포구 | 이번 고정 단계의 공 경로가 수비수 몸 축에서 수평 반경 안, 지면~최고 높이 사이를 지나면 자동으로 잡는다. 여럿이면 경로상 먼저 닿는 수비수다. 방금 던진 수비수는 0.3 s 동안 다시 잡지 않는다 | `Catch Radius` 1.0 m, `Catch Reach Height` 2.4 m |
| 뜬공 아웃 | 타구가 땅·펜스에 닿기 전에 잡으면 타자 아웃(파울 지역 포함). 모든 포스가 풀린다. 베이스를 벗어났던 누상 주자는 시작 베이스로 자동으로 돌아가 리터치해야 한다 | |
| 페어/파울 | 판정 전 땅볼을 잡으면 잡은 지점의 지역으로 정한다. 파울이면 `Foul`로 끝난다. 수비수가 한 번 닿은 뒤에는 페어/파울·홈런 판정을 하지 않는다 | |
| 송구 | 공을 가진 수비수가 1루·2루·3루·홈 중 하나를 고르면 그 베이스 위 글러브 높이(1.2 m)로 회전 없이 던진다. 실제 비행과 같은 적분으로 조준하며, 닿지 못하는 거리면 거부한다 | `Throw Speed` 30 m/s |
| 포스 | 타자주자와, 뒤 베이스가 모두 찬 누상 주자는 타구 순간 다음 베이스로 자동으로 달린다. 공을 가진 수비수가 아직 도착하지 않은 포스 베이스(홈 포함) 반경 안이면 아웃. 뒤 주자가 아웃되면 앞 주자의 포스가 풀린다 | `Base Cover Radius` 0.6 m |
| 태그 아웃 | 진루·귀루 중인(베이스에 멈추지 않은) 주자와 공을 가진 수비수의 거리가 반경 안이면 아웃 | `Tag Radius` 0.8 m |
| 리터치 | 리터치 전에 공을 가진 수비수가 그 주자의 시작 베이스를 밟으면 아웃(태그 아웃으로 기록). 리터치 뒤에는 태그업 진루할 수 있다 | |
| 플레이 종료 | ① 세 번째 아웃 ② 살아 있는 주자 없음(모두 득점·아웃) ③ 살아 있는 주자가 모두 베이스에 멈추고 리터치할 주자가 없으며 수비가 공을 가진 상태가 이어짐 → `RunnerSafe`. 득점·홈런·인정 2루타·파울·12 s 시간 초과는 기존 규칙 | `Play Dead Seconds` 1.0 s |

③의 지속 시간은 공을 잡은 순간 플레이가 죽지 않게 하려는 것이다. 그래야 태그업·추가 진루를 시도할 수 있다. 처음에는 즉시 종료였는데, 희생플라이 검증에서 주자가 태그업할 수 없는 문제로 드러나 고쳤다.

새 명령은 모두 고정 단계에서 적용한다.

- `RequestFielderMove(index, Vector2)`: 이동. 다음 명령까지 유지한다.
- `RequestFielderThrow(index, ThrowTarget)`: 송구. 한 번만 처리한다.
- `RequestRunnerDecision(slot, RunnerDecision)`: 슬롯 0 = 타자주자, 1~3 = 누상 주자.
- `RequestSetSituation(1루, 2루, 3루, 아웃)`
- `RequestScriptedBattedBall(Vector3)`: 검증·시나리오용. 투구 없이 타석 앞에서 타구를 시작한다.

새 조회와 이벤트는 다음과 같다.

- `BallHolder`, `BattedBallFielded`, `GetFielder(i)`
- `GetRunnerSnapshot(slot)`, `IsRunnerForced(slot)`, `RunnerNeedsRetouch(slot)`
- `GetSituation()`, `TryGetPlaySummary()`
- 이벤트: `BallFielded(수비수, 공중 포구 여부)`, `PlayResolved(요약)`

`PitchEndReason`에 `FlyOut`, `ForceOut`, `TagOut`, `RunnerSafe`를, `RunnerPhase`에 `Out`을 더했다. 여러 아웃이 난 플레이의 종료 사유는 마지막 아웃의 종류다. 결과 판단은 종료 사유가 아니라 `PlaySummary`로 한다.

## 수비수 Agent `BaseballFielder`

다섯 명이 같은 Behavior를 쓰고(팀 1), 역할은 관측의 원-핫으로 구분한다. `TrainingEnvController`가 `SimpleMultiAgentGroup`으로 묶어 팀 보상을 주므로 MA-POCA로 학습한다. 2026-10-01부터 내야수 세 명은 팀 보상에 더해 [내야 역할 보조 보상](#내야-역할-보조-보상-2026-10-01)을 개인 보상으로 받는다. 타구가 살아 있는 동안만 5 고정 단계(0.1 s)마다 결정하고, 사이 단계는 마지막 행동을 반복한다. 공에 닿지 않은 투구(볼·스트라이크)에서는 결정도 에피소드도 없다.

**관측 65개:**

| 항목 | 수 |
| --- | --- |
| 역할 원-핫(1B, SS, 3B, LCF, RCF) | 5 |
| 자기 위치 x/z (홈 기준) | 2 |
| 자기 속도 x/z | 2 |
| 공 소유: 자기·동료·없음 | 3 |
| 공의 상대 위치 x, 높이(지면 기준), z | 3 |
| 공 속도 | 3 |
| 타구가 땅에 닿았거나 이미 수비됨 | 1 |
| 타구 플레이 중 | 1 |
| 아웃 수 / 2 | 1 |
| 주자 슬롯 4개 × (살아 있음, 상대 x·z, 진루 중, 귀루 중, 포스, 리터치 필요) | 28 |
| 1·2·3루·홈의 상대 위치 | 8 |
| 동료 4명의 상대 위치 | 8 |

위치는 60 m, 공 속도는 40 m/s, 자기 속도는 최고 속력으로 나눈다. 2026-09-27부터 모든 위치는 자기 경기장의 홈 기준이다(자기 위치, 공 높이 포함). 그래서 경기장을 복제하거나 옮겨도 같은 상황은 같은 관측이 된다. 수비·주자 관측은 게임 상태를 그대로 읽는다. 타자처럼 레이로 "보게" 하지 않았다.

**행동:**

- 연속 2개: 이동 방향·세기 (필드 x, z)
- 이산 `[5]`: 0 송구 안 함, 1 1루, 2 2루, 3 3루, 4 홈. 공을 가진 수비수만 적용된다

`Heuristic`은 중립 행동(제자리, 송구 없음)이다.

학습기를 연결하면 `Default` Behavior는 학습기의 행동을 받는다. 다만 투구 중에는 결정을 요청하지 않으므로 타구가 나오기 전까지 기다린다. 새 수비 모델은 자동 추적 스크립트로 시작하지 않으며, 초기 무작위 행동의 작은 이동과 학습 완료된 수비를 구분해야 한다. 2026-09-30부터 3단계 두 YAML의 수비는 `batch_size=256`, `buffer_size=4096`, `summary_freq=2000`으로 초기 업데이트 대기와 지표 표시 간격을 줄였다. 동작 확인·기존 실행 재개는 [학습 안내](../Training/README.md#3단계-수비수가-서-있거나-조금만-움직일-때)를 따른다. 학습 성능은 아직 검증하지 않았다. 2026-10-01 그 설정으로 학습한 수비가 공을 쫓지 않고 경기장 밖으로 달려 나가는 것을 확인해 [수비 보조 보상](#수비-보조-보상-2026-10-01)을 더했다.

## 주자 Agent `BaseballRunner`

주자 슬롯 네 명이 같은 Behavior를 쓴다(팀 0).

- 슬롯 0: 기존 타자주자 `BatterRunner`
- 슬롯 1~3: 새 누상 주자 `BaseRunner_1B/2B/3B`. 새 타석마다 점유된 베이스에 선다

타구 순간 살아 있는 주자만 이번 플레이의 **주자 그룹**(`SimpleMultiAgentGroup`, MA-POCA)에 들어간다. 살아 있는 동안 5 고정 단계마다 결정한다.

**관측 57개:**

| 항목 | 수 |
| --- | --- |
| 슬롯 원-핫 | 4 |
| 상태 원-핫(진루·귀루·멈춤) | 3 |
| 마지막으로 밟은 베이스 원-핫 | 4 |
| 향하는 베이스 원-핫 | 4 |
| 멈출 목표 베이스 원-핫 | 4 |
| 포스 | 1 |
| 리터치 필요 | 1 |
| 위치 x/z (홈 기준) | 2 |
| 다음 베이스까지 거리 | 1 |
| 공 위치 (홈 기준) | 3 |
| 공 속도 | 3 |
| 공이 잡혔는지 | 1 |
| 공을 가진 수비수의 상대 위치 | 2 |
| 타구가 땅에 닿았는지 | 1 |
| 아웃 수 / 2 | 1 |
| 다른 주자 3명 × (살아 있음, 상대 x·z, 향하는 베이스) | 12 |
| 수비 5명의 상대 위치 | 10 |

**행동:** 이산 `[3]`. 0 판단 없음, 1 진루, 2 귀루. `RequestRunnerDecision(slot, …)`을 쓴다. `Heuristic`은 판단 없음이다. 포스된 베이스까지만 자동으로 달리고 멈춘다.

## 결과 보상

플레이가 끝나면 `PlaySummary`로 계산해 한 번 준다. 자세한 식과 예시는 [상황 규칙](game-situation.md)에 있다.

| 대상 | 규칙 |
| --- | --- |
| 수비 그룹 | 아웃마다 `+1`, 내준 베이스마다 `-0.25`, 득점마다 `-1`. 타구가 살아 있는 고정 단계마다 `-0.0005`. 여기에 아래 보조 보상. 내야수는 [개인 보조 보상](#내야-역할-보조-보상-2026-10-01)도 받는다 |
| 주자 그룹 | 전진한 베이스마다 `+0.25`, 득점마다 `+1`, 베이스 위 아웃(포스·태그·리터치 전 태그)마다 `-1`. 타자의 뜬공 아웃은 주자 책임이 아니다 |
| 타자·투수 | 타석이 끝날 때 결과 보상. 타자는 얻은 베이스·타점마다 `+0.5`, 그 플레이의 아웃마다 `-0.5`. 투수는 반대 부호 |

### 수비 보조 보상 (2026-10-01)

**배경.** 보조 보상 없이 학습한 `stage3_full_team`(수비 약 494만 스텝)을 확인했다.

- 인플레이의 약 99%가 12 s 시간 초과로 끝났다. 아웃은 플레이당 약 0.01개였고, `Runner Safe`(수비가 공을 쥔 채 플레이가 죽음)는 0이었다.
- 아웃을 얻으려면 공까지 이동 → 포구 → 포스 베이스 밟기·태그·송구와 동료 커버가 약 4 s 안에 모두 이어져야 한다. 무작위 탐색으로는 이 사슬을 거의 찾지 못해, 수비 보상이 수비 행동과 무관한 잡음이 됐다.
- 체크포인트 정책을 Python으로 재현해 보니 공 방향과 관계없이 도착 위치가 같았다. 이동 방향도 체크포인트마다 바뀌었다. 정책 평균이 신호 없이 떠돌아 파울 지역·홈 뒤쪽으로 계속 달려 나간 것이다. 이동은 홈 기준 반경 109 m 원으로만 막혀 있다.

**규칙.** 결과 보상까지 가는 중간 단계를 알려 주려고 포텐셜 기반 보조 보상(potential-based shaping)을 더했다. `PlayOutcomeRewards.DefensePotential`이 상태의 포텐셜 Φ를 정한다.

| 항목 | Φ에 더하는 값 | 기본값 |
| --- | --- | --- |
| 쫓기 (첫 포구 전) | −계수 × (공과 가장 가까운 수비수의 수평 거리). 뜬공은 공기 저항 없이 지금 속도로 떨어질 지점을 쓴다 | `DefenseChasePerMeter` 0.02 /m |
| 포구 (첫 포구 뒤) | +값. 쫓기 항목 대신 들어간다 | `DefenseFieldedValue` 0.25 |
| 포스 베이스 커버 | 아직 밟히지 않은 포스 베이스마다 −계수 × (그 베이스와 가장 가까운 수비수의 수평 거리). 공을 쥔 수비수도 포함한다 | `DefenseCoverPerMeter` 0.02 /m |

- **주는 방법:** `TrainingEnvController`가 수비 결정(0.1 s)마다 `γΦ(지금) − Φ(직전 결정)`을 수비 그룹에 준다. 첫 결정은 Φ만 기록한다. 결정 전에 더한 보상은 직전 결정의 행동 결과로 학습기에 간다.
- **끝:** 플레이가 끝나면 끝난 상태의 Φ를 0으로 보고 `−Φ(마지막 결정)`을 준다. 중단(`Interrupted`)이면 가치를 이어 받으므로 `γΦ(지금) − Φ(마지막 결정)`을 준다.
- **γ:** `DefenseShapingGamma` 0.99. 3단계 YAML의 `BaseballFielder` `gamma`와 같아야 한다.
- **정책 영향:** 한 플레이의 보조 보상 할인 합은 `−Φ(첫 결정)`이다. 첫 결정 상태는 타구 순간이라 수비 행동과 무관하다. 그래서 최적 정책은 결과 보상 그대로다. 보조 보상은 쫓기·포구·커버에 즉시 신호를 줘 학습만 돕는다.
- **TensorBoard 해석:** 할인 없는 합은 `−Φ(0) + (γ−1)ΣΦ(k≥1)`이다. Φ가 음수인 상태(공·베이스에서 먼 상태)가 길수록 오히려 커진다. 검증의 C 타구에서 제자리 수비는 +1.01이었다. `Environment/Group Cumulative Reward`와 `Defense Reward/Shaping`에는 이 할인 없는 합이 들어가므로 실력 지표로 쓰지 않는다. `Defense/Fielded`·`Defense Reward/Outcome`·`Play/*`를 본다.
- **기대 크기:** 최고 속력으로 공에 다가가면 결정마다 약 +0.015다. 시간 감점은 결정마다 −0.0025다. 첫 포구 순간에는 약 +0.25 이상이다.
- **범위:** 송구가 목표 베이스에 닿는 것에는 따로 보상을 주지 않는다. 포구·커버가 생기면 아웃 결과 보상(+1)으로 배울 것으로 봤다. 학습으로 확인한 것은 아니다.
- **기존 모델:** 관측·행동은 그대로라 2026-10-01 이전 수비 체크포인트를 읽을 수는 있다. 다만 그 가중치는 신호 없이 떠돈 결과라 이어 쓸 가치가 없다. 3단계를 새로 시작한다([학습 안내](../Training/README.md#3단계-수비-보조-보상-2026-10-01)).

### 내야 역할 보조 보상 (2026-10-01)

**배경.** 같은 날 사용자가 1·2·3루수와 나머지 수비의 보상에 차이가 있는지 물었다. 차이는 없었다.

- 결과 보상·시간 감점·위 보조 보상은 모두 수비 **그룹** 보상이다. 다섯 명이 같은 값을 받는다. 역할 차이는 관측의 원-핫뿐이다.
- 위 커버 항목은 "포스 베이스와 가장 가까운 수비수"라 누가 어느 베이스를 맡는지 정하지 않는다. 공을 쫓던 수비수가 가장 가까우면 쫓기와 커버가 같은 수비수를 반대로 당긴다.
- 내야 고유 역할에 개인 신호가 없었다. 1루수는 타자주자 포스 때문에 거의 모든 땅볼에서 1루를 밟아야 한다. 2루수가 없어 2루는 유격수가 맡는다.

**규칙.** 내야수에게 개인 포텐셜 Φ_i를 둔다(`PlayOutcomeRewards.InfieldPotential`). 외야수는 늘 0이다.

| 역할 | 맡는 베이스 | 시작 위치에서 거리 | 시작 위치의 Φ_i (쫓는 수비수가 아닐 때) |
| --- | --- | --- | --- |
| 1루수 | 1루 | 4.9 m | −0.099 |
| 유격수 | 2루 (2루수가 없다) | 9.9 m | −0.198 |
| 3루수 | 3루 | 3.9 m | −0.078 |

- **값:** Φ_i = −0.02 × (자기 베이스와의 수평 거리) (`InfieldCoverPerMeter`).
- **0인 경우:** 아래 셋은 자기 베이스보다 공 처리가 먼저다.
  - 공을 쫓는 수비수: 첫 포구 전, 위 쫓기 항목과 같은 지점에 가장 가까운 수비수(`DefenseChaser`)
  - 공을 쥔 수비수
  - 자기가 던진 공이 아직 잡히지 않은 수비수(`PlayDirector.LastThrower`)
- **주는 방법:** 그룹 보조 보상과 같다. 수비 결정마다 γΦ_i(지금) − Φ_i(직전 결정)를 주고, 끝나면 −Φ_i, 중단이면 γΦ_i(지금) − Φ_i를 준다. γ도 같은 `DefenseShapingGamma`다. 그룹이 아니라 그 수비수에게 `Agent.AddReward`로 준다. 설치된 ML-Agents 1.1.0 MA-POCA는 수비수마다 개인 보상과 그룹 보상을 더해 쓴다(`extrinsic_reward_provider.py`의 `evaluate`).
- **정책 영향:** 수비수마다 한 플레이의 할인 합이 −Φ_i(첫 결정)이다. 타구 순간 상태로 정해지므로 행동과 무관하다. 그래서 각자의 목표는 팀 목표에 상수를 더한 것이 되고, 팀 최적 정책은 그대로다.
- **기대 크기:** 최고 속력으로 베이스로 가면 결정마다 약 +0.015다. 그룹 쫓기 항목과 같은 크기다.

**설계 판단.**

- **계수는 주자 유무로 바꾸지 않는다.** 처음에는 "그 베이스로 주자가 오면 0.02, 아니면 0.01"이었다. 검토해 보니 주자가 세이프로 도착해 계수가 줄면, 멀리 있던 내야수가 바로 그 순간 양의 보상을 받는다. 나쁜 결과에 보상이 가므로 하나로 했다.
- **쫓는 수비수를 뺀다.** 빼지 않으면 쫓기와 베이스가 같은 수비수를 반대로 당긴다. 예를 들어 1루 쪽 땅볼을 쫓는 1루수가 공과 1루 사이에서 멈출 수 있다.
- **공을 쥔 수비수를 뺀다.** 직접 밟을지 던질지는 그룹 커버 항목과 결과 보상이 정한다. 쫓던 수비수가 잡으면 0 → 0이라 포구 순간에 감점이 없다.
- **송구한 수비수를 공이 잡힐 때까지 뺀다.** 빼지 않으면 던지는 순간 자기 베이스와 먼 만큼 감점된다. 3유간 땅볼을 2루에서 15 m 떨어진 곳에서 잡은 유격수가 1루로 던지면 −0.3이다. 핵심 내야 플레이(1루 송구)를 꺼리게 된다.
- **할 일 없는 내야수도 자기 베이스로 당긴다.** 보조 보상 전 수비가 경기장 밖으로 떠난 것은 행동에 신호가 없었기 때문이다. 공을 쫓지 않는 내야수가 베이스를 덮는 것은 이 환경(포수·2루수 없음)에서 기본 내야 동작이다.
- **남는 순간 변화.** 쫓는 수비수가 바뀌거나 동료가 공을 잡거나 자기 송구가 잡히면, 그 내야수의 Φ_i가 0과 −0.02 × 거리 사이를 오간다. 거리 10 m면 0.2다. 할인 합은 그대로라 정책은 바뀌지 않지만 학습 초기에는 잡음이 될 수 있다.

**한계.**

- 홈 커버(포수 없음), 중계 플레이, 백업에는 역할을 두지 않았다. 홈은 그룹 커버 항목(포스 홈)만 있다.
- 첫 포구 뒤 빠진 공(악송구)을 쫓는 개인 신호는 없다.
- MA-POCA의 중앙 가치함수는 다섯 명이 함께 쓴다. 개인 보상이 다르면 그 가치함수는 평균을 배우고, λ-반환값의 부트스트랩에 편향이 조금 생길 수 있다. 수비수별 기준선(baseline)은 자기 관측을 보므로 차이를 배울 수 있다. 학습으로 확인하지 않았다.

**지표.** `Defense/Cover 1B`·`Defense/Cover 2B (SS)`·`Defense/Cover 3B`(`TrainingStats.RecordInfieldCover`).

- **기록 대상:** 그 베이스로 진루·귀루 중인 주자가 있었던 수비 플레이마다 하나 기록한다(`IsBaseInPlay`).
- **값:** 그 동안 맡은 내야수가 베이스 반경(`Base Cover Radius` 0.6 m) 안에 들어갔으면 1, 아니면 0이다. 평균이 역할별 커버율이다.
- **직접 밟은 포스 아웃:** 공을 쥐고 베이스를 밟으면 같은 고정 단계에 주자가 아웃된다. 그래서 바로 전 단계에 주자가 오고 있었으면 센다.
- 보상이 아니라 확인용이다.

**기존 모델.** 관측·행동은 바뀌지 않았다. 보상이 바뀌었으므로 3단계 수비는 위 그룹 보조 보상과 함께 새로 시작한다.

## 검증 시나리오

`Verify Open Training Scene`을 `Stage3_FullTeam`에서 실행한다.

- 모든 Agent는 중립 행동이고 무작위 상황은 끈다.
- 각 시나리오는 `RequestSetSituation`으로 누상 주자·아웃을 정한 뒤 시나리오 타구로 시작한다.
- 수비·주루는 같은 명령 경계로 덮어쓰는 단순 스크립트다.

**스크립트 수비의 동작**

- 공을 가진 수비수: 아직 도착하지 않은 가장 앞선 포스 베이스가 12 m 안이면 직접 밟고, 멀면 그 베이스로 던진다. 포스가 없으면 리터치할 주자의 원래 베이스로, 그것도 없으면 달리는 주자가 향하는 베이스로 던진다.
- 공이 살아 있으면 예상 지점에 가장 가까운 수비수가 쫓는다.
- 커버: 1루수는 1루. 유격수는 주자가 2루로 갈 때나 1루 주자가 포스일 때 2루. 3루수는 주자가 3루로 갈 때나 2루 주자가 포스일 때 3루.

수비 보조 보상은 다음을 확인한다(2026-10-01).

- **모든 인플레이 시나리오:** 검증이 수비 결정 시점마다 Φ를 따로 모은다. 컨트롤러가 준 보조 보상 합이 `−Φ(0) + (γ−1)ΣΦ(k≥1)`과 같아야 한다. 끝난 상태의 Φ를 0으로 뒀는지, 결정마다 한 번씩만 줬는지를 본다.
- **A:** 첫 포구 결정에서 Φ가 `DefenseFieldedValue`의 80% 이상 오른다. `Defense/*` 지표가 기록된다.
- **C 다시 치기:** 같은 타구를 수비가 제자리에 선 채로 다시 친다. 첫 포구 전까지의 보조 보상 합이 스크립트 수비(쫓기·1루 커버) 쪽이 더 커야 한다. 제자리 수비는 공을 잡지 못한다(`Defense/Fielded` 0).

내야 역할 보조 보상은 다음을 확인한다(2026-10-01).

- **모든 인플레이 시나리오의 결정 시점마다:** 검증이 Φ_i를 따로 계산해 비교한다.
  - 외야수, 공을 쥔 수비수, 자기 송구가 날아가는 수비수는 0이다.
  - 나머지 내야수는 −0.02 × 자기 베이스 거리다.
  - 예외는 첫 포구 전 쫓는 수비수 한 명뿐이고 그 값은 0이다.
- **모든 인플레이 시나리오의 합:** 수비수마다 컨트롤러가 준 개인 보조 보상 합이 `−Φ_i(0) + (γ−1)ΣΦ_i(k≥1)`과 같아야 한다.
- **A:** `Defense/Cover 1B`가 1이다. 2·3루로 향한 주자가 없으므로 `Cover 2B (SS)`·`Cover 3B`는 기록되지 않는다.
- **C 다시 치기:** 첫 1초(10결정) 동안 1루수 개인 보조 보상 합이 1루로 뛴 쪽이 제자리보다 0.03 이상 크다. `Defense/Cover 1B`는 스크립트 수비 1, 제자리 0이다.
- **F:** 1루 주자가 2루로 밀려나므로 `Defense/Cover 2B (SS)`와 `Defense/Cover 1B`가 1이다.

실행 결과는 [검증](verification.md)에 둔다.
